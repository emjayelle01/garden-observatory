# Camera simulator

> **Simulated imagery is not evidence.** Everything the simulator produces is a
> drawn diagram of a bird feeder, generated in memory. It is not a photograph, it
> proves nothing about a physical camera, and it must never be entered into
> Matt's Viewings. See [Production safety](#production-safety) before enabling
> it.

## Purpose

The camera simulator is a supported **runtime backend** that lets the real Matt's
Garden Observatory pipeline run with no camera at all. It exists so that
readiness, still capture, the preview lifecycle, MJPEG streaming, browser
delivery, motion-frame consumption and status/health reporting can all be
exercised end to end on a development workstation without:

- Raspberry Pi camera hardware;
- `rpicam-*` tooling;
- `libcamera-*` tooling;
- a video device;
- a subprocess;
- an external image or video file;
- network access.

Enable it deliberately:

```toml
[camera]
enabled = true
backend = "simulator"
```

## Why the existing mocks are not enough

`MockBackend`, `MockPreviewBackend`, `MockPreviewProcess` and `MockFrameSource`
remain exactly what they always were — **test doubles**, configured from test
code. They are unchanged and still used throughout the suite. They cannot do
what the simulator does:

| | Existing mocks | Camera simulator |
| --- | --- | --- |
| Selected by | test code | `camera.backend` configuration |
| Reachable from a running app | no | yes |
| Still-image output | a fixed non-decodable byte pattern | a valid, decodable JPEG |
| Preview frames | whatever the test hands it | generated by a real bounded producer |
| Usable by the motion detector | only with hand-written frames | yes, by design |
| Runs under `uvicorn` | no | yes |

The simulator is therefore *additive*: it does not replace a mock, and no mock
was renamed or removed to make room for it.

## Runtime architecture

The simulator adds no second pipeline. It plugs into the extension boundaries the
camera domain already had:

| Existing boundary | Simulator implementation |
| ----------------- | ------------------------ |
| `CameraDetector` | `SimulatorCameraDetector` (`mgo.core.camera_detection`) |
| `CaptureBackend` | `SimulatorCaptureBackend` (`mgo.camera.simulator`) |
| `PreviewBackend` | `SimulatorPreviewBackend` (`mgo.camera.simulator`) |
| `PreviewProcess` | `SimulatorPreviewProcess` (`mgo.camera.simulator`) |
| raw MJPEG stdout pipe | `SimulatorMjpegStream` (`mgo.camera.simulator`) |

Everything downstream is the production code, untouched: `CaptureService`,
`PreviewService`, `PreviewProcessFrameSource`, `parse_mjpeg_frames`,
`MjpegBroker`, `encode_multipart_frame`, `BrokerFrameSource`,
`FrameDifferenceDetector`, the camera/motion monitors and every API route.

Selection happens through the three existing factories, so the normal
application wiring needed no change:

```text
build_detector("simulator")        -> SimulatorCameraDetector
build_capture_backend(camera_cfg)  -> SimulatorCaptureBackend
build_preview_backend("simulator") -> SimulatorPreviewBackend
```

There is no `if testing`, no `MGO_*` test override, no monkeypatch hook in
production code, no second FastAPI application and no simulator-only route. The
simulator works because it satisfies the existing protocols.

## Configuration

### Supported backend vocabulary

| Value | Meaning |
| ----- | ------- |
| `rpicam` | Physical Raspberry Pi camera through the `rpicam-*` tools. |
| `libcamera` | Physical camera through the legacy `libcamera-*` tools. |
| `simulator` | Deterministic generated imagery. **No physical camera.** |
| `null` / `none` | Deliberately unavailable; never produces an image. |

Matching is whitespace-trimmed and case-insensitive, exactly as before, so
`" Simulator "` resolves to the simulator.

### No new setting

The simulator introduces **no** configuration section and **no** new setting. A
configuration file written before the simulator existed loads with identical
values, because there is nothing new for it to be missing.

Simulator preview reuses the existing `[preview]` settings:

```toml
[preview]
enabled = true
width = 1280
height = 720
fps = 15
startup_timeout_seconds = 5.0
shutdown_timeout_seconds = 5.0
```

## Deterministic scene sequence

Frames are generated at runtime with Pillow (already a production dependency).
No image fixture is committed and nothing is downloaded.

The scene is deliberately simple and bounded: a neutral background, fixed
feeder-like shapes (a post and a tray), the static marker, and **one**
high-contrast test object that is either absent or at one of two positions.

The logical sequence is eight frames long and repeats:

| Frame | Scene |
| ----- | ----- |
| 0 | quiet scene A |
| 1 | *identical* quiet scene A |
| 2 | object present at position B |
| 3 | *identical* object at position B |
| 4 | object moved to position C |
| 5 | *identical* object at position C |
| 6 | quiet scene A |
| 7 | *identical* quiet scene A |

The identical pairs are load-bearing. They let the existing frame-difference
detector settle to `no_motion`, while the `1 -> 2`, `3 -> 4` and `5 -> 6`
transitions produce a deterministic `motion_detected`. Only three distinct
images exist, so the simulator never claims continuous motion merely because a
frame counter advanced.

### Determinism guarantees

Frame generation depends on **nothing** except the sequence index and the
requested geometry. It is independent of wall-clock time, hostname, process
identifier, random numbers and the operating system, and nothing time-varying —
no counter, no timestamp — is drawn into the image.

Within one environment, the same index and geometry always produce
byte-identical JPEG output. Across Windows and Linux the *pixel content* is
semantically identical; the compressed bytes may differ if the platform's JPEG
encoder library differs, which is why the tests compare decoded pixels for
cross-scene checks.

### The marker

Every frame carries the static visible marker:

```text
MGO CAMERA SIMULATOR
```

as dark text on a light plate in the top-left corner, clear of both object
positions. It is drawn from Pillow's **bundled bitmap font**
(`ImageFont.load_default_imagefont()`) scaled by an integer factor with
nearest-neighbour resampling: no external font file, no FreeType antialiasing,
and therefore identical on every platform. Any simulated image is identifiable
as simulated by looking at it.

## Readiness semantics

With `camera.enabled = true` and `camera.backend = "simulator"`, monitored
readiness reports:

```json
{
  "enabled": true,
  "backend": "simulator",
  "status": "available",
  "available": true,
  "detail": "Deterministic camera simulator is active; no physical camera is in use."
}
```

That detail sentence is a single shared constant
(`mgo.core.camera_detection.SIMULATOR_READINESS_DETAIL`), so the implementation,
the tests and this document cannot drift apart.

`available: true` here means *the simulator is ready to generate frames*. It is
**never** a claim about hardware. The detector deliberately reports no device
index, no sensor model, no enumerated device, no video device, no serial number
and no command output.

The detector runs no subprocess, touches no filesystem, makes no network call,
returns the same evidence every time and never raises.

`camera.enabled = false` still wins: selecting the simulator does not override
the top-level enabled gate, and readiness stays `disabled`.

No new readiness status was added. `disabled`, `waiting_for_hardware`,
`available` and `error` remain the whole vocabulary.

## Still-capture semantics

`SimulatorCaptureBackend` reports `name == "simulator"` and writes one valid,
decodable JPEG at **1280 × 720**.

The physical Camera Module 3's full 4608 × 2592 frame is deliberately *not*
imitated: generating it would cost real memory and CPU for no benefit, and the
reported metadata must describe the image that was actually produced. Capture
metadata therefore reports the real generated dimensions.

A capture flows through the whole production path — filename generation,
destination selection, directory creation, the service's own non-empty-output
verification, metadata construction, the capture archive and the
`POST /camera/capture` contract — and reports `backend: "simulator"` in the
existing field. No response field was added.

Other guarantees:

- repeated captures produce identical image content;
- no EXIF, timestamp, hostname or filesystem path is embedded (only the standard
  JFIF header);
- no subprocess is launched and no hardware is probed;
- expected filesystem failures become a `CaptureWriteError`; a raw `OSError`
  never escapes.

## Preview lifecycle

`SimulatorPreviewBackend.start(config)` validates the request and returns a
`SimulatorPreviewProcess`. Constructing that handle *is* the launch, mirroring
`subprocess.Popen`, so a producer only ever exists because the normal preview
start path asked for one.

The handle is truthful about being simulated:

| Member | Behaviour |
| ------ | --------- |
| `pid` | `None` — there is no operating-system process |
| `poll()` | `None` while active, `0` after a normal termination, `-9` after a forced kill, `1` after an unexpected producer failure |
| `terminate()` | Asks the producer to stop; settles exit code `0` |
| `kill()` | Stops the producer; settles exit code `-9` |
| `wait(timeout)` | Waits up to `timeout`; returns the code, or `None` if still running |
| `read_error()` | Empty while healthy or normally stopped; a bounded diagnostic after an unexpected failure |
| `frame_stream()` | The raw MJPEG stream |
| `close()` | Stops the producer and releases the stream |

`terminate`, `kill`, `wait` and `close` are all idempotent, and the **first**
settled exit state wins, so a later `terminate` cannot rewrite a forced kill as a
clean exit, and cleanup cannot mask a failure.

### Unexpected producer failure

A real preview process can die on its own, and the simulator is as truthful about
that as it is about a requested stop. **An explicit `terminate()`/`kill()` and an
unexpected failure are different cases and are reported differently.**

If the producer stops for any reason other than a requested stop, the handle:

- settles exit code **`1`** — never `0` or `-9`, and never leaves `poll()`
  returning `None` for a thread that is no longer alive;
- publishes a bounded single-line diagnostic through `read_error()`, built from
  the exception's class and message only:

  ```text
  Simulator frame producer failed: RuntimeError: controlled test failure
  ```

- logs the **full traceback** to the application log — the traceback never
  reaches `read_error()` or any API response;
- ends and clears the frame mailbox, so `frame_stream().read(...)` returns `b""`
  (ordinary end-of-file) once any already-delivered bytes are consumed, and every
  **blocked** reader is released promptly instead of hanging;
- lets the producer thread exit, leaving no orphan.

`poll()` additionally reconciles defensively: a producer thread that is no longer
alive while no exit state has been recorded is settled to the same failure state.
Liveness truthfulness therefore does not depend on the exception handler alone —
a future accidental early return in the producer loop is caught too. The
reconciliation is thread-safe and idempotent.

`PreviewService` needed no change to benefit from this. Its existing unexpected-exit
reconciliation observes the failure on the next `status()` (or `frame_stream()`,
or `start()`) and settles the service into the existing `FAILED` state:

```json
{
  "state": "failed",
  "owner": null,
  "uptime_seconds": null,
  "last_error": "Preview process terminated unexpectedly with code 1: Simulator frame producer failed: RuntimeError: controlled test failure"
}
```

When the sequence fails *before* its first frame, startup fails instead: the
existing first-frame validation sees end-of-file, `PreviewStartError` is raised
carrying code `1` and the bounded diagnostic, and the state is `FAILED` — never
`RUNNING`. No new state, status value or response field was introduced for any of
this.

Through the API the lifecycle is unchanged:

- preview starts `stopped`;
- `POST /camera/preview/start` starts it;
- `GET /camera/preview/status` reports `running` with `backend: "simulator"`;
- `GET /camera/preview/stream` delivers generated frames;
- `POST /camera/preview/stop` stops it;
- application shutdown reaps it;
- a capture releases an active preview and does **not** restart it (the existing
  capture-priority policy).

No preview status value was added, and opening `/dashboard` or `/preview` starts
nothing.

## MJPEG stream design

`frame_stream()` returns a blocking binary stream of **concatenated complete
JPEG frames** — the same raw Motion-JPEG promise `rpicam-vid --codec mjpeg`
makes — so the existing `parse_mjpeg_frames` SOI/EOI demultiplexer consumes it
unchanged. The streaming parser was **not** modified for the simulator.

`SimulatorMjpegStream` is a real `io.RawIOBase`: a read blocks until the next
frame is available and returns zero bytes (ordinary end-of-file) once the stream
has ended.

The first complete JPEG is published immediately on start, so `PreviewService`'s
startup validation — which reads the first complete frame — succeeds well inside
`startup_timeout_seconds`. After that first frame has been consumed, later
readers continue receiving subsequent frames from the same process.

Browser delivery uses the existing `PreviewProcessFrameSource`, `MjpegBroker` and
`encode_multipart_frame`, including the broker's generation ownership: many
viewers share the one producer, a slow viewer drops frames rather than growing
memory, and losing the last viewer closes only the broker's source — preview
keeps running and no second camera owner is created.

## Motion compatibility

The generated frames are consumed by the **existing** motion pipeline:
`BrokerFrameSource` -> `FrameDifferenceDetector` -> the motion monitor. Neither
the algorithm nor its thresholds were changed, and the simulator creates no
motion detector, bypasses no JPEG decoding, fabricates no `MotionResult`, writes
no observation and never touches motion state.

Measured with the production defaults (analysis 160 × 90, per-pixel threshold 20,
changed-pixel ratio threshold 0.08):

| Transition | Changed-pixel ratio | Result |
| ---------- | ------------------- | ------ |
| identical pair (`0 -> 1`, `2 -> 3`, `4 -> 5`, `6 -> 7`) | `0.000` | `no_motion` |
| object appears (`1 -> 2`) | ≈ `0.117` | `motion_detected` |
| object moves (`3 -> 4`) | ≈ `0.236` | `motion_detected` |
| object leaves (`5 -> 6`) | ≈ `0.119` | `motion_detected` |

Every score is finite and within `[0, 1]`, and the threshold reported by
`GET /motion/status` remains the configured one.

## Safety bounds

The simulator generates every pixel itself, so it carries its own explicit
ceiling rather than trusting a configuration file:

| Bound | Value |
| ----- | ----- |
| minimum frame width / height | 160 × 120 |
| maximum preview width | 1920 |
| maximum preview height | 1080 |
| maximum preview frame rate | 30 fps |
| still-capture resolution | 1280 × 720 |
| frames retained for a slow consumer | 2 |

An unsafe request is **refused, never silently clamped**. A bad width, height or
frame rate raises `PreviewStartError` — the existing preview-domain failure model,
surfaced by the API as it always was — with a concise message naming only the
setting and its bounds:

```text
Simulator preview frame rate must be between 1 and 30.
```

No path, environment variable or other environment detail appears in that
message.

## Threading and shutdown

Exactly **one** bounded daemon producer thread (`mgo-simulator-preview`) exists
per preview process. It:

- publishes the deterministic sequence at the configured frame rate;
- waits on a stop event between frames, so there is no busy loop *and* shutdown
  is immediate rather than delayed by a frame;
- writes into a mailbox holding at most two frames, discarding the **stale**
  frame when the consumer falls behind — a slow reader costs a dropped frame,
  never memory;
- releases any blocked reader promptly on `terminate`, `kill` or `close`, so a
  waiting read ends at clean end-of-file instead of hanging;
- contains any unexpected fault: it is logged with its traceback and settled as
  the failure state described above, rather than killing the thread silently.
  `KeyboardInterrupt`, `SystemExit` and `GeneratorExit` are deliberately **not**
  caught;
- exits on stop *or* on failure, leaving no orphan behind a preview stop, a
  capture, repeated start/stop cycles, a producer failure or application shutdown;
- is a daemon, so it can never keep the interpreter alive.

Shutdown never joins the calling thread against itself, and the exit-state lock is
never held while the mailbox is ended, so no combination of `poll`, `terminate`,
`kill`, `wait`, `close` and a failing producer can deadlock.

No `subprocess`, `multiprocessing`, shell, local HTTP server or temporary video
file is involved. The module imports none of them.

## How to run locally

Use a **temporary** configuration and temporary storage outside the repository.
Never point this at `config/mgo.toml`, the repository development database,
`/etc/garden-observatory/mgo.toml` or `/var/lib/garden-observatory`.

Write a scratch `mgo.toml` somewhere temporary:

```toml
[application]
name = "Matt's Garden Observatory"
environment = "development"
host = "127.0.0.1"
port = 8125

[storage]
data_directory = "<temp>/data"
log_directory  = "<temp>/logs"
database_path  = "<temp>/data/mgo.db"

[camera]
enabled = true
backend = "simulator"
detection_interval_seconds = 60
capture_directory = "<temp>/data/captures"

[preview]
enabled = true
width = 1280
height = 720
fps = 15
startup_timeout_seconds = 5.0
shutdown_timeout_seconds = 5.0

[motion]
enabled = true
analysis_interval_seconds = 1.0
analysis_width = 160
analysis_height = 90
pixel_difference_threshold = 20
changed_pixel_ratio_threshold = 0.08
cooldown_seconds = 5.0

[notifications]
enabled = false
provider = "log"

[health]
enabled = true
collection_interval_seconds = 60
temperature_warning_celsius = 70.0
temperature_critical_celsius = 80.0
disk_warning_percent = 80.0
disk_critical_percent = 90.0
memory_warning_percent = 85.0
memory_critical_percent = 95.0
```

Then run the application against it, bound to loopback only:

```bash
MGO_CONFIG_PATH=/tmp/mgo-simulator/mgo.toml uv run uvicorn mgo.api.app:app --host 127.0.0.1 --port 8125
```

On Windows PowerShell:

```powershell
$env:MGO_CONFIG_PATH = "$env:TEMP\mgo-simulator\mgo.toml"; uv run uvicorn mgo.api.app:app --host 127.0.0.1 --port 8125
```

Then open `http://127.0.0.1:8125/preview` in a browser: the generated scene
appears, with the marker plainly visible.

## How to validate without hardware

The automated suite covers the whole simulator contract and needs no camera, no
tooling and no network:

```bash
uv run pytest tests/test_camera_simulator.py
```

A useful sequence against a running local simulator instance:

| Step | Expectation |
| ---- | ----------- |
| `GET /camera/status` | `backend: simulator`, `status: available`, the truthful detail |
| `GET /camera/preview/status` | `state: stopped` initially |
| `POST /camera/preview/start` | 200, `state: running`, `backend: simulator` |
| `GET /camera/preview/stream` | `multipart/x-mixed-replace`, complete decodable JPEGs |
| `GET /motion/status` | progresses past `waiting_for_frames` |
| `POST /camera/capture` | 200, `backend: simulator`, a decodable file on disk |
| `GET /captures` | lists the capture |
| `POST /camera/preview/stop` | 200, `state: stopped` |

Delete the temporary database, captures and configuration afterwards.

Producer failure is validated separately, because it cannot be provoked through
the API: a controlled in-process run injects a fault into frame generation and
confirms that `poll()` reports `1`, `read_error()` carries the bounded diagnostic,
a blocked reader is released at end-of-file, `PreviewService.status()` reconciles
to `failed`, and no producer thread survives. See
`tests/test_camera_simulator.py` — the *unexpected producer failure* section.

## API behaviour

No endpoint was added, removed or renamed, and no response field was removed or
given a new meaning. The single externally visible change is that the existing
`backend` fields — in `GET /camera/status`, `GET /health`,
`GET /camera/preview/status`, `POST /camera/capture`, `GET /captures` and
`GET /captures/{id}` — may truthfully contain `simulator`.

There is deliberately **no** separate "is simulated" flag. The `backend` field is
the single source of that truth, so no client can read one without the other.

## Privacy and metadata

Generated images carry no private data:

- no EXIF block at all (only the standard JFIF density header);
- no timestamp, hostname, username, process identifier or filesystem path;
- no location or device identity;
- nothing derived from the machine that generated them.

Nothing is fetched from the network, and no external asset or binary media
fixture is committed to the repository.

## Production safety

The simulator is **opt-in**. The default configuration is unchanged and remains
hardware-safe (camera disabled, `backend = "rpicam"`), and
`config/mgo.production.example.toml` remains configured for the real Raspberry Pi
backend. An operator must deliberately set `backend = "simulator"` before any
simulated imagery can appear.

Understand clearly what simulator mode does **not** give you:

- **simulated captures are not wildlife evidence** — they are drawings;
- **simulator readiness does not prove physical camera readiness** — it proves
  only that the software path works;
- **simulator preview does not validate focus, exposure, field of view or window
  reflections** — none of those exist in a generated scene;
- **Task 12 physical camera acceptance remains required** and is not replaced by
  anything here;
- **simulator captures must not be entered into Matt's Viewings**;
- **simulator output is unsuitable as a bird-identification training dataset** —
  it contains no birds, only a rectangle.

The simulator always identifies itself, through the `backend` field and through
the readiness detail, so no status response can be mistaken for hardware
evidence.

## Limitations

- Only three distinct images exist; the simulator models scene *change*, not
  realistic imagery, lighting, noise or motion blur.
- The moving object is a plain rectangle. It is not a bird and is not intended to
  resemble one.
- Compressed JPEG bytes may differ across platforms whose JPEG encoder libraries
  differ; the pixel content is semantically deterministic, and byte-determinism
  is guaranteed within one environment.
- The producer paces itself on a stop-event wait, so the achieved frame rate is
  approximate under heavy load — as it would be for a real encoder.
- Nothing here exercises camera ownership contention with a *real* process,
  because there is no real process.
- A producer failure is reported through one failure code (`1`) and a bounded
  message; the simulator does not classify *kinds* of internal fault, because a
  real preview process does not either.

## Rollback

Before merge: switch back to `main`. The simulator branch has no production
effect — no migration, no schema change, no dependency change, no configuration
value change and no deployment change.

After a future merge: revert the Task 11 commits, re-run the test suite, and
redeploy `main` if required.

No database rollback and no migration rollback are required. No media cleanup is
needed unless an operator deliberately ran a simulator capture with a
non-temporary capture directory — in which case delete those files, which are
identifiable by their `simulator` backend in the capture archive.

## Relationship to Task 12

Task 12 is **physical camera acceptance on the Raspberry Pi**, and the simulator
does not substitute for any part of it. What the simulator can do is remove the
software-only failure modes *before* the Pi is involved, so a physical
acceptance run is testing the camera rather than the plumbing.

## Future use

Later work can reuse the simulator as a deterministic frame source rather than
building its own fixtures:

- **event capture** — driving the pre/post-event window logic with a repeatable
  motion sequence;
- **detection and identification** — exercising the wiring, queueing and
  persistence of an inference stage without needing real footage (the imagery
  itself is useless for training or accuracy measurement);
- **regression testing** — reproducing a stream-handling defect deterministically
  on any workstation.

None of that is implemented here; the simulator is the frame source those
features may later choose to use.
